# Architecture Decision Records

## 철학
MVP 속도 최우선. 외부 의존성 최소화. 작동하는 최소 구현을 선택한다. 단, 금융 데이터를 다루므로 **격리(RLS)와 산술 정확성**은 타협하지 않는다.

---

### ADR-001: Supabase를 인증 + DB로 채택
**결정**: Supabase Auth(이메일 + 소셜) + Postgres + RLS를 한 세트로 쓴다.
**이유**: 계정당 데이터 격리를 애플리케이션 코드가 아니라 DB 정책으로 강제할 수 있다. 금융 데이터에서 이 차이는 크다 — 쿼리에 `where user_id =`를 빼먹어도 RLS가 막는다. 무료 티어로 MVP가 끝난다.
**트레이드오프**: Supabase에 락인된다. RLS 정책 디버깅은 애플리케이션 레벨 필터보다 어렵다.

### ADR-002: 결제는 Polar
**결정**: `@polar-sh/nextjs` 어댑터로 Checkout / CustomerPortal / Webhooks를 붙인다.
**이유**: Merchant of Record라 세금·인보이스를 대신 처리한다. Next.js App Router 어댑터가 공식 제공되어 라우트 3개로 결제가 끝난다. 고객 포털도 제공되므로 구독 관리 UI를 직접 만들 필요가 없다.
**트레이드오프**: 국내 간편결제(카카오페이·네이버페이)를 지원하지 않는다. 초기 타겟이 카드 결제로 충분하다는 전제.

### ADR-003: 산술은 코드가, 언어는 LLM이
**결정**: 금액 집계·기간별 추이·반복 결제 탐지·이상치 판정은 TS/SQL로 계산한다. LLM은 ① 가맹점명 카테고리 분류, ② 집계 결과의 한국어 요약·절약 제안, 두 가지에만 쓴다.
**이유**: LLM 산술은 틀려도 그럴듯해서 검증이 불가능하다. 사용자가 "이 합계 왜 이래?"라고 물었을 때 답할 수 있어야 한다. 또한 거래 원문 전체를 프롬프트에 넣으면 명세서 한 건에 수만 토큰이 든다 — 가맹점 유니크 목록만 보내면 수백 토큰이다.
**트레이드오프**: 반복 결제 탐지 규칙(간격·금액 편차 임계값)을 직접 튜닝해야 한다. LLM에 통째로 맡기는 것보다 초기 구현이 길다.

### ADR-004: Claude structured outputs로 스키마 강제
**결정**: `claude-opus-5` + `output_config.format`(json_schema)로 분류·인사이트 응답을 스키마에 고정한다.
**이유**: 파싱 실패 재시도 로직이 필요 없어진다. 카테고리는 enum으로 제한해 모델이 새 카테고리를 지어내지 못하게 막는다.
**트레이드오프**: 카테고리 목록이 코드에 하드코딩된다. 사용자 정의 카테고리는 MVP 범위 밖.

### ADR-005: 거래 원본을 전량 보관
**결정**: 업로드된 거래를 개별 행으로 저장하고, 원본 CSV 행도 `transactions.raw`(jsonb)에 남긴다.
**이유**: 요구된 분석 중 "기간별 지출 추이"와 "구독 누수 탐지"는 여러 달치가 누적돼야 성립한다. 요약만 저장하면 이 두 기능이 불가능하다. `raw`를 남기면 컬럼 매핑 로직을 고쳤을 때 재업로드 없이 재처리할 수 있다.
**트레이드오프**: 유출 시 피해 범위가 크다. 이를 상쇄하기 위해 (a) 카드·계좌번호는 파싱 단계에서 마스킹, (b) 모든 테이블 RLS 강제, (c) 계정 삭제 시 cascade 삭제를 필수로 둔다.

### ADR-006: 요금제는 횟수가 아니라 보관 기간 + 기능으로 나눈다
**결정**: Free/Pro 모두 업로드·분석 무제한. Free는 최근 3개월 조회 + 분류/추이까지, Pro는 무제한 보관 + 구독 누수 탐지 + AI 인사이트 + 내보내기.
**이유**: 명세서는 월 1회 나온다. 횟수를 제한하면 유료 전환 압박이 아니라 그냥 제품이 안 쓰이게 된다. 반면 이력이 쌓일수록 가치가 커지는 구조라 보관 기간이 자연스러운 과금 축이 된다.
**운영 가드레일**: 상품상 월간 횟수 제한과 남용 방지는 별개다. 인증 사용자별 단기 업로드 제한과 동일 명세서의 동시·반복 분류 방지를 둔다. 이 제한은 정상적인 월별 사용을 막는 요금제 기능이 아니라 비용 공격과 실수성 재요청을 막는 안전장치다.
**트레이드오프**: Free 사용자도 LLM 분류 비용을 발생시킨다. 가맹점 유니크 목록만 보내는 구조라 감당 가능하다고 판단.

### ADR-007: 초과 보관 데이터는 삭제하지 않고 가린다
**결정**: Free 플랜에서 3개월을 넘긴 거래는 조회 쿼리에서 제외하고 UI에 잠금 표시한다. 물리 삭제하지 않는다.
**이유**: 삭제하면 업그레이드해도 복구가 안 되고, 사용자 입장에서 "내 데이터를 지웠다"는 최악의 경험이 된다. 가려두면 이미 쌓인 이력 자체가 업그레이드 동기가 된다.
**트레이드오프**: 이탈한 무료 사용자의 데이터가 계속 쌓인다. 이를 상쇄하기 위해 **계정 삭제 경로를 MVP 범위에 넣는다**(ADR-005의 원본 전량 보관과 합쳐지면 떠난 사용자의 금융 거래 원문이 무기한 남기 때문). 장기 미접속 자동 정리 정책은 운영 데이터를 보고 정한다.

### ADR-008: 업로드를 저장과 분류 2단계로 나눈다
**결정**: `POST /api/statements`는 파싱·저장까지만 하고 즉시 응답한다. LLM이 필요한 작업(카테고리 분류, 인사이트 생성)은 `POST /api/statements/[id]/classify`가 맡는다.
**이유**: 분류는 LLM 호출이라 10~30초가 걸리고 실패할 수 있다. 한 요청으로 묶으면 분류가 실패했을 때 파싱 결과까지 함께 잃고 재시도할 방법이 없다. 나눠두면 거래는 이미 저장돼 있고 분류만 다시 돌리면 된다. 사용자도 2초 만에 거래 목록을 본다.
**트레이드오프**: 클라이언트가 호출을 두 번 해야 하고 "분류 중" 상태를 관리해야 한다. 또한 1단계만 끝난 채 방치된 명세서가 생길 수 있으므로 대시보드에 미분류 배너와 재분류 액션이 필요하다.
**정정**: 이 결정의 근거는 Vercel 함수 타임아웃이 아니다. fluid compute 기준 기본 300초라 동기 호출도 죽지 않는다. 근거는 실패 복구와 체감 속도다.

### ADR-009: 가맹점→카테고리 맵은 테이블이 아니라 쿼리다
**결정**: 이미 분류된 `transactions`에서 `distinct on (merchant)` 로 맵을 뽑는다. 분류는 이 맵에 없는 가맹점에 대해서만 LLM을 호출한다. 전용 테이블을 만들지 않는다.
**이유**: 명세서는 매달 온다. 맵이 없으면 지난달에 분류한 가맹점이 이번 달에 또 미분류로 들어와 같은 질문을 LLM에 반복한다. 그런데 그 정보는 **이미 `transactions.category`에 있다** — 테이블을 하나 더 만들면 같은 사실이 두 곳에 적히고, 둘을 동기화하는 규칙(사용자 수정 우선, 거래 삭제 시 정리)이 따라붙는다. 쿼리 한 줄이면 사본 없이 끝난다. `order by (category_source = 'user') desc` 가 사용자 수정 우선순위까지 처리한다.
**트레이드오프**: 매 업로드마다 맵 쿼리가 한 번 돈다. `(user_id, merchant)` 인덱스가 있고 가맹점 수는 수백 단위라 무시할 수준이다. 가맹점명 정규화가 어긋나면 같은 가게가 두 항목으로 갈리는 위험은 그대로이므로, 정규화 규칙은 `lib/csv.ts` 한 곳에만 둔다.

### ADR-010: 게이팅은 기능이 아니라 목록 단위로 건다
**결정**: 구독 탐지와 이상 거래는 Free에서도 **건수와 총액을 계산해 보여주고** 세부 목록만 잠근다. AI 인사이트는 전체를 잠근다.
**이유**: "뭐가 빠져나가는지 모르겠다"가 유입 동기인 사용자에게 구독 탐지를 통째로 잠그면 첫 방문에 가치를 하나도 못 본 채 떠난다. 게다가 반복 결제는 3회 이상 누적돼야 탐지되므로, 1회차에 아무것도 못 보여주면 3회차 방문은 오지 않는다. 요약 수치는 실제 계산 결과이므로 가짜 데이터를 보여주는 것이 아니다.
**트레이드오프**: Free 사용자에게도 탐지 연산을 돌려야 한다. 전부 코드 계산이라 비용은 무시할 수준이다. AI 인사이트를 네 번째 전환 벽으로 쓰지 않는 이유는, 근거가 되는 목록이 잠긴 상태에서 그 근거로 쓴 글만 파는 것이 순서가 거꾸로이기 때문이다.
**따름정리**: **보관 기간 필터는 표시에만 적용하고 탐지 계산에는 적용하지 않는다.** 월간 구독이 3회 쌓이려면 90일이 걸리므로, Free의 90일 컷오프를 탐지 입력에 먼저 걸면 이 ADR이 약속한 수치가 대부분 0이 되어 무의미해진다.

### ADR-011: LLM 호출은 쓰기 경로에서만 한다. 페이지 렌더에서 부르지 않는다
**결정**: `classifyMerchants`와 `generateInsights`는 둘 다 업로드 2단계(`POST /api/statements/[id]/classify`)에서만 호출한다. Server Component와 컴포넌트는 `transactions.category`와 `insights` 테이블을 **읽기만** 한다.
**이유**: LLM 호출은 10~30초다. Server Component 렌더 안에서 부르면 그 시간만큼 페이지 응답이 통째로 막히고, 실패하면 대시보드 전체가 죽는다. 캐시 미스가 나는 첫 방문이 가장 느린 방문이 되는 것도 거꾸로다 — 첫인상이 가장 중요한 순간인데.
**트레이드오프**: 인사이트가 아직 없는 구간이 생긴다. 그때는 `"인사이트를 준비하고 있습니다."` + 생성 버튼을 렌더한다. 조회 경로에 LLM이 없다는 규칙은 지키기 쉽고 `grep`으로 검증된다.

### ADR-012: 권한 상승이 가능한 값은 사용자 쓰기 경로에서 분리한다
**결정**: `profiles.plan`과 `subscriptions.*`에는 사용자 UPDATE 정책을 만들지 않는다. 결제 대상 user id는 서버 세션에서만 읽고, 쿼리 파라미터로 들어온 값은 세션과 대조해 다르면 거부한다.
**이유**: RLS는 행 단위 정책이라 UPDATE를 허용하면 그 행의 모든 컬럼이 열린다. `profiles`에 통상적인 `auth.uid() = id` UPDATE 정책을 붙이면 브라우저에서 `update({ plan: 'pro' })` 한 줄로 결제를 우회할 수 있다. 같은 이유로 Polar 체크아웃의 `customerExternalId`를 클라이언트가 정하게 두면, 남의 계정에 내 구독을 연결해 그 사람의 플랜을 좌우할 수 있다.
**트레이드오프**: 나중에 `profiles`에 사용자가 편집할 컬럼(닉네임 등)이 생기면 정책 대신 컬럼 단위 권한(`grant update (col) on profiles to authenticated`)을 써야 한다. 행 정책 하나로 끝내는 것보다 번거롭지만, 권한 컬럼과 프로필 컬럼이 한 테이블에 있는 한 이게 유일하게 안전한 방법이다.

### ADR-013: 파생값은 저장하지 않고 조회 시점에 계산한다
**결정**: 반복 결제, 이상 거래, 카테고리별 합계, 기간별 추이, 가맹점→카테고리 맵을 DB에 저장하지 않는다. 전부 `transactions`를 입력으로 하는 순수 함수의 결과이므로 필요할 때 계산한다. 저장하는 것은 원본(`transactions`)과 외부 호출 결과(`insights`)뿐이다.
**이유**: 파생값을 저장하면 테이블마다 RLS 정책, 유니크 제약, 그리고 **원본이 바뀔 때 맞춰주는 코드**가 따라붙는다. 실제로 초안에서는 `recurring_charges`를 매 업로드마다 UPSERT 하면서 정작 대시보드는 `detectRecurring()`을 다시 호출하고 있었다 — 쓰기만 하고 아무도 읽지 않는 테이블이었다. 명세서를 지울 때 재계산해야 한다는 규칙도 이 테이블 때문에 생겼다. 계산은 수천 행에 대한 순수 함수라 밀리초 단위다.
**인사이트 무효화**: `insights`는 외부 호출 결과라 저장하지만 거래 집합과 카테고리를 입력으로 만든 캐시다. 명세서 삭제 또는 사용자 카테고리 수정으로 입력이 바뀌면 같은 트랜잭션에서 해당 사용자의 `insights` 행을 삭제한다. 다음 업로드 분류 전까지 대시보드는 `"인사이트를 준비하고 있습니다."` 상태를 보여준다. 오래된 인사이트를 새 데이터의 결과처럼 표시하지 않는다.
**트레이드오프**: 이력이 커지면 매 조회마다 전체를 훑는 비용이 는다. 탐지를 위해 전체 이력을 한 번 조회하므로 Pro 이력이 매우 커지면 부담이 생길 수 있다. MVP 규모에서는 허용하고, 실제로 느려지면 SQL 집계나 캐시 테이블을 추가한다.
